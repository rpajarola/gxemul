Introduction

The built-in debugger is made for a person at a terminal. The control socket gives programs (scripts, test harnesses, AI agents) the same kind of access, with structured requests and replies: pausing and continuing the machine, single-stepping, breakpoints, reading what the guest wrote to its serial consoles and typing into them, and any debugger command at all.

It is enabled with --control: 

$ gxemul --control unix:/tmp/gx.sock -e 3max -d ultrix.img

The terminal and its GXemul> prompt keep working as usual alongside it.

The control socket has no authentication. Anyone who can connect to it can read and change the emulated machine's memory and registers, so a TCP socket only listens on 127.0.0.1, and a Unix socket is protected by the permissions of the directory it is in.


The command line client

gxemul --ctl sends one request and prints the reply, so that each step is one shell command: 

gxemul --ctl socket [--wait] [--timeout seconds] command [argument]

socket is the same as given to --control. The argument is either a JSON object with the request's parameters, or, for the commands below, a plain value for their main parameter:

raw  line
stepn
break_addpc
break_delid
console_readsince

symbolname, or addr if it starts with a digit
run_untila console pattern (console.pattern)

The reply is printed as one line of JSON. With --wait, after a successful continue, step, run_until or pause, the client also waits for the machine to stop (or exit), and prints that event too. The exit code is 0 for success, 1 if the emulator replied with an error, 2 if the socket could not be used, and 3 if --timeout expired while waiting. (A timeout leaves the machine running.) 

$ gxemul --control unix:/tmp/gx.sock -V -e 3max -d ultrix.img &
$ gxemul --ctl unix:/tmp/gx.sock break_add panic
{"id":1,"ok":true,"result":{"id":1,"addr":"0xffffffff8004c1a8","expr":"panic"},"ninstrs":0}
$ gxemul --ctl unix:/tmp/gx.sock --wait --timeout 300 continue
{"id":1,"ok":true,"result":{"already_running":false},"ninstrs":0}
{"event":"stopped","reason":"breakpoint","bp":1,"cpu":0,"pc":"0xffffffff8004c1a8","ninstrs":901238877}
$ gxemul --ctl unix:/tmp/gx.sock console_read 0
$ gxemul --ctl unix:/tmp/gx.sock raw "reg"
$ gxemul --ctl unix:/tmp/gx.sock raw "unassemble pc-16 pc+16"

Since each --ctl is its own connection, events that happen between two of them are not seen by anyone. status tells how the machine last stopped, and console output is kept by the emulator until it is read, so nothing important is lost.


Transport and framing

  • --control unix:path listens on a Unix domain socket (not on Windows). An old socket at path is replaced; any other kind of file there is an error.
  • --control tcp:port listens on 127.0.0.1. Port 0 picks a free port, which is printed at startup.
  • Each message is one line of JSON (UTF-8), ending with a newline.
  • There is one client at a time. While one is connected, another connection gets {"ok":false,"error":{"code":"busy",...}} and is closed.
  • Requests are handled by the emulator's own thread, between the slices of instructions it runs. A request never sees a CPU in the middle of an instruction, so registers and memory can be read consistently even while the machine runs.


Requests, responses and events

A request names a command, and may carry an id of the client's choosing, which is copied to the response: 

{"id": 7, "cmd": "break_add", "pc": "memcpy+0x40"}

Each request gets exactly one response, in the order the requests were sent: 

{"id": 7, "ok": true, "result": {"id": 3, "addr": "0xffffffff80012340", "expr": "memcpy+0x40"}, "ninstrs": 1203}
{"id": 7, "ok": false, "error": {"code": "bad_arg", "message": "couldn't parse 'memcpy+0x40'"}, "ninstrs": 1203}

Events come unasked, have no id, and are never put inside another message's line: 

{"event": "stopped", "reason": "breakpoint", "bp": 3, "cpu": 0, "pc": "0xffffffff80012340", "ninstrs": 1203}

Conventions:

  • Addresses and register values are strings in hexadecimal, as JSON numbers can't hold 64-bit values exactly.
  • Where an address is given, it can also be a number, or any expression the debugger understands, such as "panic", "memcpy+0x40" or "sp+16".
  • Every response and event has ninstrs: the number of instructions the first machine's boot CPU has run. It is the clock for relating things to each other.


Running and stopped

The emulator is either running or stopped (at the debugger prompt). continue, step and pause reply right away; when the machine then stops, a stopped event follows.

Reading works in both states, as does run_until. Changing the machine (step, reg_set, mem_write) needs it stopped. A stop caused at the terminal (CTRL-C, or typing step) sends a stopped event to the client too, and a continue from the client continues the terminal's prompt.


Commands

Session and control

cmdparametersresult
hello proto (1), version, state, machines (each with name and cpus: id, name, arch, bits, endian), consoles (id, name, machine), default_console
status state, stop (how it last stopped, as in the stopped event; absent if it never stopped), cpus (id, pc, halted: stopped by the guest or the emulator, not just paused)
pause already_stopped; if false, a stopped event with reason pause follows
continue already_running
stepn (default 1) empty; a stopped event with reason step follows after n instructions
quit empty; then an exited event, and the connection closes

Breakpoints

cmdparametersresult
break_addpc (an address) id, addr, expr
break_delidempty
break_list breakpoints: list of id, addr, expr

A breakpoint's id never changes, unlike the numbers shown by the debugger's breakpoint show, which are positions in the list.

Registers and memory

cmdparametersresult
regs cpu (default: the debugger's current CPU), names (a list; default: all) cpu, regs: an object of register names and values, in the CPU's order
reg_set cpu, name, value (an expression) value, as now stored
mem_read addr, len (default 64, at most 1 MB), space ("virtual" or "physical"), cpu addr, data (hex), and fault_at if only part could be read
mem_write addr, data (hex), space, cpu written, and fault_at if only part could be written

The registers are those the debugger knows by name (as in print pc or a0 = 5), for any kind of CPU; values are as wide as the register. Memory is accessed as the debugger does it: through the CPU's address translation, without causing exceptions, so an unmapped address gives the error mem_fault rather than a guest fault. Code which has been written is translated again.

Code and symbols

cmdparametersresult
disasm addr (default: pc), count (default 10, at most 1000), cpu instructions: list of addr, bytes (hex, in memory order), text, and symbol if the address is in one
symbol name, or addr name, addr (where the symbol starts), and with addr, the offset into it

text is the instruction as the debugger's unassemble shows it, after the address: on MIPS, the instruction word, an arrow at the pc, and the instruction.

Running until something happens

cmdparametersresult
run_until one or more of: console ({"pattern": ..., "console": ..., "since": ..., "input": ...}), pc, insns, timeout_ms already_running; with console, console_offset (where the search starts), and with input, written

Continues the machine (if stopped) until the first of the conditions happens; it then stops with reason run_until, and the condition which happened:

  • console: the console printed one of the patterns, a string or a list of strings (plain text, not regular expressions). The event has the match, and the console_offset just after it. The search starts at what is printed from now on, or at offset since. input is typed into the console after the search starts, so its reply can't be missed: {"console": {"pattern": ["login:", "panic"], "input": "boot\r"}}
  • pc: an address is reached (as a breakpoint, which is removed again).
  • insns: this many more instructions have run.
  • timeout_ms: this many milliseconds have passed.

Console patterns, insns and timeout_ms are checked every few milliseconds, so the machine stops a little after them (and may have printed more after the match); pc is exact. If the machine stops for any other reason, such as a breakpoint, the run_until is over. A new run_until replaces one which is still waiting.

Serial consoles

cmdparametersresult
console_read console (default: the machine's main console), since (default 0), max (default 65536), encoding ("text" or "hex") data, start, offset, dropped
console_write console, data, encoding written

The emulator keeps the last 1 MB written to each console, counted by a byte offset which only grows. console_read returns what was written from offset since on: start is the offset of the first byte returned, and offset is where to continue next time. dropped is true if part of what was asked for is no longer kept. With "text", bytes 0x80-0xff come back as the characters U+0080-U+00FF, and NUL bytes are left out; "hex" gives the bytes exactly.

console_write types into the console, as if from its terminal. Text is sent as its UTF-8 bytes. written may be less than the length if the console's input buffer is full; write the rest later.

Any debugger command

cmdparametersresult
rawline text: what the command printed

raw runs a line as if typed at the GXemul> prompt, such as "reg", "dump 0x80001000", "tlbdump" or "device list". Use pause, continue and step rather than their raw forms, to get the events right.


Events

{"event":"stopped", "reason":..., "cpu":0, "pc":"0x...", "ninstrs":N}
{"event":"stopped", "reason":"run_until", "condition":"console", "match":"login:", "console_offset":N, ...}
{"event":"exited", "ninstrs":N}

The reason for a stop is one of:

  • breakpoint (the event also has bp, the breakpoint's id)
  • step
  • pause (asked for by the client)
  • run_until (with the condition which happened)
  • user (CTRL-C, or the display's menu)
  • startup (started with -V)
  • unimplemented_instruction
  • all_stopped (all CPUs stopped, with -V)
  • other


Error codes

  • bad_request: not a JSON object, or no cmd
  • unknown_cmd
  • bad_arg: a parameter is missing or can't be used
  • not_stopped: the command needs a stopped machine
  • no_such_cpu, no_such_console, no_such_breakpoint, no_such_symbol
  • mem_fault: nothing could be read or written at the address
  • capture_failed: the output of raw or the disassembler could not be captured
  • busy: another client is connected


Planned additions

  • tlb and devices, with structured results.
  • stop_on: stop on exceptions of a kind, or on accesses to a device's registers.
  • A trace ring buffer: the last instructions, exceptions and device accesses before a stop.
  • subscribe, for console and log events as they happen.
