GXemul: DECstation emulation

Back to the index.

The DECstation emulation mode is the oldest full machine mode in GXemul, and probably still the most complete one. The specific model being emulated best is the 5000/200. When emulating that model, the following guest operating systems can be installed and run:

  • NetBSD/pmax
  • OpenBSD/pmax
  • Ultrix/RISC
  • Sprite
  • Debian GNU/Linux

In addition to the working operating systems above, you may also want to read half-finished notes on how to run RedHat Linux/DECstation and Mach/PMAX.

Setting up a 5000/200: The guides below run the 5000/200's own firmware, as on a real machine, from a machine.json in a folder of its own. This needs ROM images, dumped from a real 5000/200 (see below), which gxemul looks for in the machine's folder and in the ROM folders:

"rom"  the system ROM, KN02-AA V5.3s (e.g. kn02_aa_5.3s.bin)
slot 0the PMAG-BA framebuffer's option ROM (pmag_ba_5.3a.bin), with the display on
slot 5the PMAZ-AA SCSI controller's option ROM (pmaz_aa_5.3d.bin)
slot 6the PMAD-AA Ethernet interface's option ROM (pmad_aa_5.3a.bin)

With "nvram", the firmware's settings are kept in a file. At the ROM's >> prompt, boot 5/rz4/vmunix boots vmunix from the disk or CD-ROM with SCSI ID 4 on the SCSI controller in slot 5; setenv boot "..." sets what boot alone boots; printenv shows the settings, and cnfg the hardware. Instead of the window, gxemul --vnc tcp:5900 machine.json shows the screen to a VNC client.

Without ROM images, GXemul can also start a kernel itself (PROM emulation, as in gxemul -X -e 3max -d disk.img netbsd), which is handy for quick tests, but the guides below use the real firmware.

The default processor in the emulated DECstation 5000/200 is a 32-bit MIPS R3000, but many of the guest operating systems are also capable of running with a 64-bit MIPS R4400, by adding -C R4400 to the command line.

Most of the other models in the DECstation/DECsystem family are not emulated well enough to run anything meaningful. One exception is the 5000/1xx, aka 3MIN. If you are able to make a backup copy of the PROM from your own machine, then you can try to run that in the emulator. The 5000/200's own PROM can also be run, with dumps of the option ROMs of its SCSI controller and Ethernet interface. With a real PROM, an HX framebuffer (1280x1024) can be used instead of the default one.


NetBSD/pmax:

NetBSD/pmax was the first guest OS that could be installed onto a disk image in GXemul.

NetBSD/pmax installs on the 5000/200 from its CD, with the machine's real ROMs. This was tested with NetBSD 10.1; for NetBSD 11.0, see below.

  1. Download the CD image, NetBSD-10.1-pmax.iso, and make a folder for the machine, with the ROM images, an empty disk image, and this machine.json:
    {
  "gxemul": 1,
  "name": "NetBSD/pmax 10.1",
  "machine": { "type": "decstation", "model": "3max", "memory_mb": 128 },
  "boot": { "prom_emulation": false, "rom": "kn02_aa_5.3s.bin", "nvram": "nvram.bin" },
  "drives": [ { "file": "disk.img", "kind": "disk", "id": 0 },
              { "file": "NetBSD-10.1-pmax.iso", "kind": "cdrom", "id": 4, "readonly": true } ],
  "display": { "enabled": true },
  "slots": { "0": "pmag_ba_5.3a.bin", "5": "pmaz_aa_5.3d.bin", "6": "pmad_aa_5.3a.bin" }
}

    	$ truncate -s 2000M disk.img
	$ gxemul machine.json
  2. The ROM asks for the keyboard's language (4 is English; setenv console 1 stops it from asking again). Boot the CD:
    	>>boot 5/rz4/netbsd
  3. Install with sysinst: install NetBSD to the hard disk (sd0), with the default partition sizes, the full installation, from the CD-ROM, and set root's password. Then reboot, and boot the disk from the ROM:
    	>>setenv boot "5/rz0/netbsd -a"
	>>boot
    (Without -a, NetBSD boots single-user. setenv haltaction b makes the ROM boot it at power-on.)

Log in as root, and type startx to start X. Without the display ("enabled": false, and no ROM in slot 0), the console is the serial line, in the terminal GXemul runs in.

NetBSD 11.0's CD does not boot, in GXemul or on a real DECstation: its installation kernel is so big that loading it overwrites the boot loader (NetBSD's PR port-pmax/45147). The installed system's kernel is smaller, and boots. So install 11.0 with the 10.1 installer, from the 11.0 CD:

  1. Add both CDs to the machine.json above, the 11.0 CD as rz4 (sysinst takes the sets from the first CD-ROM drive) and the 10.1 CD as rz5:
      "drives": [ { "file": "disk.img", "kind": "disk", "id": 0 },
              { "file": "NetBSD-11.0-pmax.iso", "kind": "cdrom", "id": 4, "readonly": true },
              { "file": "NetBSD-10.1-pmax.iso", "kind": "cdrom", "id": 5, "readonly": true } ],
  2. Boot the 10.1 installer from the second CD, and install as above:
    	>>boot 5/rz5/netbsd
    (sysinst calls the result NetBSD 10.1, but the sets, the kernel, and the boot loader on the disk are 11.0's.)
  3. Boot the disk the same way as 10.1:
    	>>boot 5/rz0/netbsd -a
    The first boot waits a minute for entropy.


OpenBSD/pmax:

OpenBSD/pmax died at release 2.8 of OpenBSD, so this will not give you an up-to-date OpenBSD system. It installs on the 5000/200 with the machine's real ROMs, from the release's simpleroot (a small root file system with the installer, on a disk of its own) and a CD image of the release's files. This was tested with the files from OpenBSD/2.8/pmax.

  1. Download that directory (approx. 99 MB), unpack the simpleroot, and make a CD image of the directory (with mkisofs, or xorriso -as mkisofs):
    	$ gunzip -c pmax/simpleroot28.fs.gz > simpleroot28.fs
	$ mkisofs -r -o openbsd-2.8-pmax.iso pmax
	$ truncate -s 1000M disk.img
    Install on the serial console, which is faster than the framebuffer, with this machine.json (and the ROM images) in the same folder:
    {
  "gxemul": 1,
  "name": "OpenBSD/pmax 2.8",
  "machine": { "type": "decstation", "model": "3max", "memory_mb": 64 },
  "boot": { "prom_emulation": false, "rom": "kn02_aa_5.3s.bin", "nvram": "nvram.bin" },
  "drives": [ { "file": "disk.img", "kind": "disk", "id": 0 },
              { "file": "simpleroot28.fs", "kind": "disk", "id": 1 },
              { "file": "openbsd-2.8-pmax.iso", "kind": "cdrom", "id": 2, "readonly": true } ],
  "display": { "enabled": false },
  "slots": { "5": "pmaz_aa_5.3d.bin", "6": "pmad_aa_5.3a.bin" }
}
  2. Boot the simpleroot's kernel, with the simpleroot (rz1) as the root device, and start the installer from its shell:
    	>>boot 5/rz1a/bsd
	...
	root device? rz1
	Enter pathname of shell or RETURN for sh: (press Return)
	# fsck /dev/rrz1a
	# mount /dev/rz1a /
	# mkdir -p /kern /mnt2
	# mount -t kernfs /kern /kern
	# cd /; ./install
  3. Answer the installer's questions: don't install onto the simpleroot's disk, the root disk is rz0, and create a label in the disklabel editor, e.g. a root partition and swap:
    	> a a                  (offset 0, a size, 4.2BSD, mount point /)
	> a b                  (the rest, swap)
	> w
	> q
    No more file systems, no network, and install from the CD-ROM: c, rz2, partition c, cd9660, and the directory .; then extract each set (two Returns each).
  4. The installer neither sets root's password (it is empty) nor installs the X11 sets. Do that from the same shell, and halt:
    	# mount /dev/rz0a /mnt
	# chroot /mnt passwd root
	# mount -t cd9660 /dev/rz2c /mnt2
	# cd /mnt; for s in xbase xfont xserv xshare; do tar -xzpf /mnt2/${s}28.tgz; done
	# ln -s Xcfbpmax /mnt/usr/X11R6/bin/X
	# ln -s /dev/fb0 /mnt/dev/mouse
	# echo /usr/X11R6/lib >> /mnt/etc/ld.so.conf
	# cd /; umount /mnt2; umount /mnt; halt
  5. Turn the display on ("enabled": true, and the PMAG-BA's ROM in slot 0, as in the Ultrix example), and boot the new system:
    	>>setenv boot "5/rz0a/bsd -aN"
	>>boot
    (-a boots multi-user, and N takes the root device from where the kernel was loaded, instead of asking.)

When asked for the terminal type when logging in as root, enter rcons on the framebuffer (vt100 on the serial console). Use startx to start X.


Ultrix/RISC:

Ultrix/RISC 4.x was DEC's own operating system for these machines, and installs on the 5000/200 from its CD, with the machine's real ROMs. (This was tested with Ultrix and UWS 4.5.)

  1. Make a folder for the machine, with the ROM images, an empty disk image of an RZ26's size, and this machine.json:
    {
  "gxemul": 1,
  "name": "Ultrix 4.5",
  "machine": { "type": "decstation", "model": "3max", "memory_mb": 64 },
  "boot": { "prom_emulation": false, "rom": "kn02_aa_5.3s.bin", "nvram": "nvram.bin" },
  "drives": [ { "file": "disk.img", "kind": "disk", "id": 0, "product": "RZ26     (C) DEC" },
              { "file": "ultrix-4.5.iso", "kind": "cdrom", "id": 4, "readonly": true } ],
  "display": { "enabled": true },
  "slots": { "0": "pmag_ba_5.3a.bin", "5": "pmaz_aa_5.3d.bin", "6": "pmad_aa_5.3a.bin" }
}

    	$ truncate -s 1050M disk.img
	$ gxemul machine.json
    Keep the display on during the installation: the installation configures a kernel for the hardware it finds, and without the framebuffer, Ultrix's console stays on the serial line afterwards.
  2. The ROM asks for the keyboard's language (4 is English). Then boot the CD:
    	>>boot 5/rz4/vmunix
    (5 is the TURBOchannel slot of the SCSI controller, and rz4 the drive with SCSI ID 4.)
  3. Choose the BASIC installation, and the RZ26 (rz0) as the system disk. The installation restores the root file system, and halts. Boot the system disk, as it says:
    	>>setenv boot "5/rz0/vmunix -a"
	>>boot
  4. Answer the questions: the system's name, the date (as yymmddhhmm), the time zone, root's password, the display (Color), and the user interface (DECwindows for OSF/Motif). The installation then loads the software, builds a kernel, and reboots to the DECwindows login box.

Two settings of the ROM make the machine start like an installed workstation (they are kept in nvram.bin):

	>>setenv console 1
	>>setenv haltaction b
console 1 stops the ROM from asking for the keyboard's language at every reset, and with haltaction b, it boots the boot setting at power-on instead of stopping at its prompt. boot 5/rz0/vmunix (without -a) boots single-user.

Before logging in at the login box, see the graphical login logs out right away below.

If you want TCP/IP IPv4 networking, try executing the following inside ULTRIX as root: 

ifconfig ln0 10.0.0.1
route add default 10.0.0.254 1

This will allow you to e.g. telnet to numeric IPv4 addresses.

The kernel that the installation built only knows about the hardware that was there; with other hardware (e.g. more graphics cards), boot the generic kernel, genvmunix, instead of vmunix. Older versions of GXemul used X11, and could show each window on a different X11 display. The photo below shows a single Ultrix session running triple-headed that way, in GXemul on an Alpha 21164PC, with displays on a Sun Ultra1 (to the left), on the Alpha itself (in the middle), and on an HP700/RX X-terminal (8-bit color depth, running off the Alpha) to the right.

The graphical login logs out right away: With Ultrix 4.5 (and possibly other versions), logging in at the graphical login box can return to the login box immediately, without an error message. Ultrix starts the session with /etc/ttys running login -P /usr/bin/Xprompter -C /usr/bin/dxsession -e :0, and login leaves the login box (Xprompter) as a child of dxsession. The login box exits once the session starts. On a real machine, loading the 4 MB dxsession from disk takes long enough that this happens first, but the emulated disk is so fast that dxsession is already watching its children, takes the exit as the end of its session, and logs out. (init then logs "'/usr/bin/login -P /usr/bin/Xprompter ...' failing, sleeping".)

The workaround is to keep a shell between login and dxsession, so that the login box becomes the shell's child instead, and to start dxsession a little later, once the login box is gone. (Without the delay, the session still ended right away in about half of the logins.) Boot single-user (boot 5/rz0/vmunix, without -a), and replace the /usr/bin/dxsession link with a small script:

	fsck -p
	mount -a
	mv /usr/bin/dxsession /usr/bin/dxsession.orig
	echo '#!/bin/sh' > /usr/bin/dxsession
	echo 'sleep 2' >> /usr/bin/dxsession
	echo '/usr/bin/X11/dxsession "$@"' >> /usr/bin/dxsession
	chmod 755 /usr/bin/dxsession
	sync
and boot multi-user (exit continues to multi-user). (The script must not exec the real dxsession, since that would replace the shell. To undo it, move dxsession.orig back.)

No ln0 interface on Ultrix 3.1: Ultrix 3.1 finds the Ethernet as ln0 while booting ("ln0 at ibus6", and in uerf), but the driver registers the network interface as se0, so ifconfig ln0 fails with "no such interface". Use se0 instead (for example in /etc/rc.local): ifconfig se0 10.0.0.5 netmask 255.0.0.0 up. Ultrix 4.x calls both of them ln0.

A note for the historically interested: OSF/1 for MIPS was quite similar to Ultrix, so that is possible to run as well. If you are unsuccessful in installing Ultrix or OSF/1 directly in the emulator, you can always install it on your real machine onto a real SCSI disk, and then copy the contents of that SCSI disk into a file (using dd(1)), and use that file as a disk image file in the emulator.


Sprite for DECstation:

Sprite was a research operating system at the University of Berkeley. A copy of a Sprite harddisk image for a DECstation 5000/200 is still available. If you want to find out more about Sprite in general, read https://web.stanford.edu/~ouster/cgi-bin/spriteRetrospective.php.

Sprite runs from that disk image on the 5000/200, with the machine's real ROMs:

  1. Download the Sprite harddisk image (it is also on the Sprite CD, as ds5000.bt):
    https://github.com/OSPreservProject/sprite/raw/master/ds5000.bt

(83973120 bytes, MD5 = ec84eeeb20fe77b758370d5e312e4a5e)
  2. Make a folder for the machine, with the disk image, the ROM images, and this machine.json. Sprite keeps its Ethernet address on the disk, so give the machine a fixed one ("mac"), which the Ethernet interface's ROM then reports:
    {
  "gxemul": 1,
  "name": "Sprite",
  "machine": { "type": "decstation", "model": "3max", "memory_mb": 128 },
  "boot": { "prom_emulation": false, "rom": "kn02_aa_5.3s.bin", "nvram": "nvram.bin" },
  "drives": [ { "file": "ds5000.bt", "kind": "disk", "id": 0 } ],
  "display": { "enabled": true },
  "slots": { "0": "pmag_ba_5.3a.bin", "5": "pmaz_aa_5.3d.bin", "6": "pmad_aa_5.3a.bin" },
  "network": { "mac": "08:00:2b:e0:e0:25" }
}
  3. Start it with gxemul machine.json. The ROM asks for the keyboard's language (4 is English; setenv console 1 stops it from asking again). Then boot Sprite:
    	>>setenv boot "5/rz0/vmsprite"
	>>boot
    (setenv haltaction b makes the ROM boot it at power-on.)

The first time you boot up with the disk image, you will be asked a number of questions regarding network settings. If you feel like entering correct values, then you should use the following: 

    Your machine's Ethernet address:    8:0:2b:e0:e0:25     (the "mac" above)
    Your machine's IP:                  10.0.0.1
    Subnet mask:                        0xff000000
    Gateway's Ethernet address:         60:50:40:30:20:10
    Gateway's IP:                       10.0.0.254
    Nameserver's IP:                    10.0.0.254

Unfortunately, at the end of https://raw.githubusercontent.com/OSPreservProject/sprite/master/boot.txt, the following sad statement can be found: 

    The bootable Sprite image is meant to be a demonstration of Sprite, not
    a robust Sprite system.  There are several missing things, such as 
    floating point and network support.

Once you are logged in as root, running xinit will start the X11 environment.

Networking: The emulated Ethernet works, but the disk image needs a few changes before Sprite can use it. Sprite has no ifconfig: the kernel only sends and receives raw Ethernet frames (and its own RPC), TCP/IP is a user-level daemon, /sprite/daemons/ipServer, and ARP requests are answered by another daemon, /sprite/daemons/arpd. Both read the hosts and their addresses from /etc/spritehosts, and ipServer also reads /etc/ipServer.config. Its log is /hosts/hostname/ip.out.

Log in as root, and:

  1. Fix the gateway line in /etc/ipServer.config. The setup script writes the gateway's Ethernet address before its IP address, but ipServer wants name IP Ethernet, for example:
    	Start_Gateways
	gateway		10.0.0.254	60:50:40:30:20:10
	End_Gateways
  2. The network device files in the disk image have unit number 0, which matches no protocol, so every write to them fails with "Rte_OutputPacket: invalid argument" in ip.out and nothing is received. Make them again (device type 8; the unit is 0x4000 plus the protocol: 1 for ARP, 2 for RARP, 3 for IP):
    	rm /dev/etherIP /dev/etherARP /dev/etherRARP
	fsmakedev -d 8 -u 16387 /dev/etherIP
	fsmakedev -d 8 -u 16385 /dev/etherARP
	fsmakedev -d 8 -u 16386 /dev/etherRARP
	restartIPServer
  3. Start arpd, so that other hosts can find Sprite's Ethernet address (the Sprite kernel doesn't answer ARP requests for its IP address itself), and add the same line to /boot/bootcmds to start it at every boot:
    	/sprite/daemons/arpd

ipServer never sends ARP requests either. It only knows the Ethernet addresses of the hosts in /etc/spritehosts, and sends everything else to the gateway's Ethernet address. When a reply comes back, it learns the sender's address from it, so hosts on the same network usually work if the gateway forwards the first packet. Hosts that are used often can be added to /etc/spritehosts, in the same format as the line for Sprite itself, followed by restartIPServer. (netroute uses the same file for Sprite's own RPC, so give other hosts Sprite IDs that no Sprite machine uses.)


Debian GNU/Linux for DECstation:

Debian GNU/Linux 3.1 ("sarge") installs on a 5000/1xx (3MIN) from its netinst CD, with the machine's real ROMs. It doesn't work on the 5000/200: its Linux 2.4 kernel has no keyboard driver for the 5000/200's DZ serial chip ("lk201: support for DZ11 not yet ready"), and its DZ driver copies up to 4 KB of output into a buffer of a few hundred bytes, which overwrites other kernel data and crashes the installer.

The 5000/1xx's ROM is kn02_ba_5.7j.bin (KN02-BA V5.7j); its SCSI controller and Ethernet are built in, and the PMAG-BA framebuffer (pmag_ba_5.3a.bin) goes in slot 0. The ROM's self-test reports a few failures (cache, cursor and clock tests that GXemul doesn't pass yet) and then waits at the >> prompt instead of booting by itself.

  1. Download the CD image, debian-31r6a-mipsel-netinst.iso, and make a folder for the machine, with the ROM images, an empty disk image, and this machine.json:
    {
  "gxemul": 1,
  "name": "Debian 3.1",
  "machine": { "type": "decstation", "model": "3min", "memory_mb": 128 },
  "boot": { "prom_emulation": false, "rom": "kn02_ba_5.7j.bin", "nvram": "nvram.bin" },
  "drives": [ { "file": "disk.img", "kind": "disk", "id": 0 },
              { "file": "debian-31r6a-mipsel-netinst.iso", "kind": "cdrom", "id": 4, "readonly": true } ],
  "display": { "enabled": true },
  "slots": { "0": "pmag_ba_5.3a.bin" }
}

    	$ truncate -s 2000M disk.img
	$ gxemul machine.json
  2. Boot the installer from the CD. On the 5000/1xx, the built-in SCSI controller is slot 3, and the CD's boot loader (delo) takes a partition number and a label:
    	>>boot 3/rz4 1/linux-kn02
    Linux takes a minute to start, and the installer a few more. If you add parameters, give them all, since they replace delo's: boot 3/rz4 1/linux-kn02 initrd=/boot/initrd.gz ramdisk_size=8192 console=ttyS2 installs on the serial console (without the display, and without slot 0).

  3. Install: the keyboard layout step fails (there is no layout for the LK201); continue with Detect and mount CD-ROM. The network is configured with DHCP. Choose Erase entire disk, with all files in one partition. Installing the base system from the CD takes about an hour. delo goes on /dev/sda.
  4. The installer reboots to the ROM. Boot the disk:
    	>>boot 3/rz0
    The second part of the installation asks for the keymap (choose Keep kernel keymap), the time zone, root's password, and a user. The CD isn't accepted as an apt source, and "stable" on the archive isn't sarge any more: cancel the apt configuration, choose Finish configuring the base system, and then point apt at the archive:
    	# echo deb http://archive.debian.org/debian sarge main > /etc/apt/sources.list
	# apt-get update

If the system was installed on the serial console, its delo label boots with console=ttyS2, and the logins on the virtual consoles are switched off. For the framebuffer and keyboard, add a label without it to /etc/delo.conf, and remove the # in front of the 1:2345:respawn:/sbin/getty 38400 tty1 line in /etc/inittab:

label=fb
  image=/vmlinux
  append="root=/dev/sda1"

	>>setenv boot "3/rz0 1/fb"
	>>boot

Redhat Linux for DECstation:

The following steps should let you run Redhat Linux for DECstation in GXemul:

  1. Download a kernel. David Muse' Debian-install kernel works fine:
    	http://www.firstworks.com/mips-linux-2.4.31/vmlinux-2.4.31
  2. Download a root filesystem tree:
    	ftp://ftp.linux-mips.org/pub/linux/mips/mipsel-linux/root/mipsel-root-20011216.tgz
	19486676 bytes, md5 = 5bcb725c90209479cd7ead8ad0c4a414
  3. Create a disk image which will contain the Redhat filesystem:
    	dd if=/dev/zero of=redhat_mips.img bs=1024 count=1 seek=2000000
  4. This is the tricky part: on redhat_mips.img, you need to create an MS-DOS (!) partition table, and then an ext2 partition. This is what Linux will then see as /dev/sda1.

    I recommend you run fdisk and mke2fs and untar the archive from within Debian/DECstation or Debian/CATS running inside the emulator. (Alternatively, if you are on a Linux host, you could use a loopback mount, or similar. This might require root access. See e.g. http://www.mega-tokyo.com/osfaq2/index.php/Disk%20Images%20Under%20Linux.)

    In order to actually boot the system you need to modify /etc/fstab. Change

    	/dev/root               /               nfs     defaults        1 1
	#/dev/sdc1              /               ext2    defaults        1 1
	none                    /proc           proc    defaults        0 0
	none                    /dev/pts        devpts  mode=0622       0 0
    to
    	#/dev/root              /               nfs     defaults        1 1
	/dev/sda1               /               ext2    defaults        1 1
	none                    /proc           proc    defaults        0 0
	none                    /dev/pts        devpts  mode=0622       0 0
    (Note sda1 instead of sdc1.)

To boot Redhat linux from the disk image, use the following command line:

	gxemul -X -e3max -o "root=/dev/sda1 ro" -d redhat_mips.img vmlinux-2.4.31

If you need to boot into single user mode, change options to -o "root=/dev/sda1 rw init=/bin/sh".


Mach/PMAX:

Read the following link if you want to know more about Mach in general: http://www-2.cs.cmu.edu/afs/cs/project/mach/public/www/mach.html

NOTE: Mach for DECstation requires some files (called 'startup' and 'emulator') which I haven't been able to find on the web. Without these, Mach will not get very far. These installation instructions are preliminary.

The following steps should let you experiment with running Mach for DECstation in the emulator:

  1. Download the pmax binary distribution for Mach 3.0:
    	http://lost-contact.mit.edu/afs/athena/user/d/a/
	    daveg/Info/Links/Mach/src/release/pmax.tar.Z
	7263343 bytes, md5 = f9d76c240a6e169921a1df99ad560cc0
  2. Extract the Mach kernel:
            tar xfvz pmax.tar.Z pmax_mach/special/mach.boot.MK83.STD+ANY
  3. Create an empty disk image:
    	dd if=/dev/zero of=disk.img bs=1 count=512 seek=400000000
  4. Load the contents of pmax.tar.Z onto the disk image. This is complicated, and should be described in more detail some time. For now, use your imagination, for example using OpenBSD/pmax: 
    	disklabel -E rz1; newfs -O /dev/rz1a;
	mount /dev/rz1a /mnt; cd /mnt; download pmax.tar.Z using ftp;
	tar xzvf pmax.tar.Z; mv pmax_mach/* .; rmdir pmax_mach;
	mkdir mach_servers;
	cd mach_servers;
	cp ../etc/mach_init .;
	cp ../tests/test_service startup;
	dd if=/dev/zero of=paging_file bs=65536 count=400;
	cd /; sync; umount /mnt

  5. Start the emulator with the following command:
    	gxemul -c 'put w 0x800990e0, 0' -c 'put w 0x80099144, 0' \
	    -c 'put w 0x8004aae8, 0' -e 3max -X -d disk.img \
	    pmax_mach/special/mach.boot.MK83.STD+ANY

Earlier versions of GXemul had a configure option to enable better R3000 cache emulation, but since Mach was more or less the only thing that used it, I removed it. Today's version of GXemul can thus not boot mach.boot.MK83.STD+ANY straight off, it has to be patched to skip the cache detection.

The -c commands above patch the kernel to get past the cache detection. Thanks to Artur Bujdoso for these values.

DECstation 5000/1xx with raw PROM image:

First, make a dump of the PROM from your own 5000/1xx. The easiest way is to hook up a serial console. The terminal must be able to capture output to a file.

These are approximately the commands that I used: 

        >>cnfg                             Show machine configuration

        >>printenv                         Show environment variables

        >>setenv more 0                    This turns off the More messages

        >>e -x 0xbfc00000:0xbfffffff       Dump the PROM data

Remember that DECstations are little endian, so if the dump data looks like this: 

        bfc00000:  0x0bf0007e

then the bytes in memory are actually 0x7e, 0x00, 0xf0, and 0x0b.

At 9600 bps, about 10KB can be dumped per minute, so it takes a while. Once enough of the PROM has been dumped, you can press CTRL-C to break out. Then, restore the more environment variable: 

        >>setenv more 24

Now, convert the data you just saved (little-endian words -> bytes), and store in a file. Let's call this file DECstation5000_125_promdump.bin. 

        $ decprom_dump_txt_to_bin DECstation5000_125_promdump.txt DECstation5000_125_promdump.bin

This binary image can now be used in the emulator: 

	$ gxemul -e 3min -Qx -M128 0xbfc00000:DECstation5000_125_promdump.bin

	KN02-BA V5.7e   
	?TFL:  3/scc/access (1:Ln1 reg-12: actual=0x00 xpctd=0x01) [KN02-BA]
	?TFL:  3/scc/io (1:Ln0 tx bfr not empty. status=0X 0) [KN02-BA]
	...
	--More--?TFL: 3/scsi/cntl (CUX, cause= 1000002C)
	>>?
	 ? [cmd]
	 boot [[-z #] [-n] #/path [ARG...]]
	 cat SCRPT
	 cnfg [#]
	 d [-bhw] [-S #] RNG VAL
	 e [-bhwcdoux] [-S #] RNG
	 erl [-c]
	 go [ADR]
	 init [#] [-m] [ARG...]
	 ls [#]
	 passwd [-c] [-s]
	 printenv [EVN]
	 restart
	 script SCRPT
	 setenv EVN STR
	 sh [-belvS] [SCRPT] [ARG..]
	 t [-l] #/STR [ARG..]
	 unsetenv EVN
	>>cnfg
	 3: KN02-BA  DEC      V5.7e    TCF0  (128 MB)
	                                     (enet: 00-00-00-00-00-00)
	                                     (SCSI = 7)
	 0: PMAG-BA  DEC      V5.3a    TCF0
	>>printenv
	 boot=
	 testaction=q
	 haltaction=h
	 more=24
	 #=3
	 console=*
	 osconsole=3
	>>

(The goal is to get rid of the test failures indicated by the PROM's tests, but it will take quite some time as there are other things to work on in the emulator as well. Also, making the PROM accept the graphics card and keyboard so that it boots with console on framebuffer would be nice.)

Some of the tests fail only because GXemul doesn't emulate what they check: on the KN02-BA V5.7j, 3/cache/seg and 3/cache/isol (a real R3000 data cache) and 3/rtc/time (real-time I/O timing), on the PMAG-BA V5.3a, 0/curs and 0/ptrn (the Bt459's signature registers), and on the PMAGB-BA V1.1, two parts of 0/patt and 0/line (the HX's signature registers). With "skip_failing_tests": true in the machine.json ("Skip the self-tests that fail only in gxemul" on the Firmware page of the configuration window), GXemul loads a copy of these ROM images in which those tests pass at once; the ROM images themselves aren't changed. (experiments/patch_rom_tests.py makes such copies by hand.)

The PROM keeps its settings (setenv: e.g. boot and console) in the NVRAM of the real-time clock. With "nvram": "nvram.bin", they are kept in that file, from one run of the machine to the next.

The command line options used are: -e 3min for "DECstation 3min" (5000/1xx), -Q to supress the emulator's own PROM call emulation, -M128 for 128MB RAM (because GXemul doesn't correctly emulate memory detection well enough for the PROM to accept, so it will always believe there is 128MB ram anyway), and -x is used to give each serial port a TCP port for telnet. The 0xbfc00000 in front of the filename tells GXemul that it is a raw binary file which should be loaded at a specific virtual address.


DECstation 5000/200 with raw PROM and option ROM images:

The 5000/200's PROM has no drivers of its own for the built-in SCSI controller and Ethernet interface: like the options in the other TURBOchannel slots, they have option ROMs (in slots 5 and 6), which hold their diagnostics and their boot code. Without dumps of those ROMs, the PROM runs, but can't boot from a disk. With them, it boots as on a real 5000/200. Choose the DECstation 5000/200 in the configuration window, and add the images under Firmware (where slots 5 and 6 are listed with the system ROM image); in the machine.json, they are: 

{
  "gxemul": 1,
  "name": "DECstation 5000/200 (ROM)",
  "machine": { "type": "decstation", "model": "3max", "memory_mb": 128 },
  "boot": { "prom_emulation": false, "rom": "decstation5000_200.bin" },
  "drives": [ { "file": "osf1.dsk", "kind": "disk", "id": 0 } ],
  "slots": { "5": "pmaz-aa.bin", "6": "pmad-aa.bin" }
}

(Slot 5 is the SCSI controller, a PMAZ-AA, and slot 6 the Ethernet interface, a PMAD-AA.)

The PROM then finds the disks with the SCSI ROM's own driver: 

	KN02-AA V5.3s    (PC: 0x0, SP: 0xa0007f00)
	>>cnfg
	 7: KN02-AA  DEC      V5.3s    TCF0  (0220cpu with 128 MB memory)
	 6: PMAD-AA  DEC      V5.3a    TCF0  (enet: 10-20-30-00-00-10)
	 5: PMAZ-AA  DEC      V5.3d    TCF0  (SCSI = 7)
	 0: PMAG-BA  DEC      V5.3a    TCF0
	>>cnfg 5
	 5: PMAZ-AA  DEC      V5.3d    TCF0  (SCSI = 7)
	    ---------------------------------------------------
	    DEV   PID                VID        REV    SCSI DEV
	    ===== ================== ========== ====== ========
	    rz0   RZ58     (C) DEC   DEC        2000   DIR
	>>boot 5/rz0/vmunix -a

(-a boots OSF/1 multi-user; without it, it comes up single-user.)

An option ROM is one byte wide, with each byte in its own 32-bit word of the slot's address space; an option ROM image has one ROM byte per byte of the file (the low byte of each word). experiments/dump_tc_rom.py dumps a ROM over a real DECstation's serial console into such a file. The slot 5 and 6 ROMs are soldered to the 5000/200's system module, but the ROM of an option card can be dumped the same way, and loaded in its slot.

The diagnostics in the PMAZ-AA and PMAD-AA ROMs pass (e.g. t 5/cntl, t 5/sram). Some of the PROM's own tests of the system module (slot 7: caches, serial lines, and memory ECC) fail, as those are not emulated in that detail.


HX (PMAGB-BA) framebuffer, 1280x1024:

A framebuffer in a TURBOchannel slot is a PMAG-BA (CX), with 1024x864 pixels at 8 bits per pixel. When the slot is given the option ROM image of a PMAGB-BA (HX), it is an HX instead, with 1280x1024 pixels at 8 bits per pixel. Its SFB ("smart frame buffer") chip draws for the X server: fills, stipples, lines and copies, with raster operations and plane masks. There is no built-in ROM image for the HX, so it needs a real system ROM too ("prom_emulation": false). The HX's ROM V1.1 is in MAME's ds5k133 ROM set as pmagb-ba-rom.img, together with the 5000/1xx system ROM; with ds5k133.zip in a ROM folder, the names alone are enough: 

{
  "gxemul": 1,
  "name": "DECstation 5000/133 with an HX",
  "machine": { "type": "decstation", "model": "3min", "memory_mb": 128 },
  "boot": { "prom_emulation": false, "rom": "ds5000-133_005eb.bin" },
  "drives": [ { "file": "ultrix.dsk", "kind": "disk", "id": 0 } ],
  "slots": { "0": "pmagb-ba-rom.img" }
}

On a 5000/200, add "0": "pmagb-ba-rom.img" to the slots of the example above. In the configuration window, the image goes in slot 0, on the Firmware page.

The system ROM finds the card (cnfg shows 0: PMAGB-BA DEC V1.1 TCF0 (HX -- d=8 )), and its console is on the HX's screen. Ultrix 4.5 (with the fb device, as in genvmunix), its X server and DECwindows run at 1280x1024, on the 5000/200 and on the 5000/1xx.

Two parts of the HX ROM's self-tests read signature registers that GXemul doesn't compute: the Signature Analysis of 0/patt and the Line Signature Mode of 0/line. "skip_failing_tests": true (see above) makes them pass.
